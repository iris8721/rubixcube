# rubixcube

Interactive 3D Rubik's cube simulator written in C++20 on top of [raylib](https://www.raylib.com/), with a from-scratch implementation of Kociemba's two-phase solving algorithm — no external solver library.

## Features

- Real-time 3D cube rendering with animated face turns (raylib + rlgl)
- Manual face turns via keyboard or on-screen buttons
- Random 25-move scrambler
- **Sticker-paint mode**: click any sticker to cycle its color, then validate the painted state against cubie legality (color counts, corner/edge orientation, permutation parity) and solve it directly
- Kociemba two-phase solver with IDA* search, move tables, and BFS-generated pruning tables
- Step mode: walk through the computed solution one move at a time
- Debug overlay: solve time, solution length, phase-1/phase-2 depths, and node counts
- Toggleable cubie/sticker rendering and UI panels

## How the solver works

The solver (`kociemba_solver.cpp`) is a clean-room implementation of Herbert Kociemba's two-phase algorithm. The cube is represented at the cubie level — corner permutation/orientation and edge permutation/orientation — rather than as 54 stickers.

**Phase 1** searches for a sequence that brings the cube into the subgroup where all corners are untwisted, all edges are unflipped, and the four UD-slice edges occupy the middle layer. The state is compressed into three coordinates:

- corner twist (3^7 = 2187 states)
- edge flip (2^11 = 2048 states)
- UD-slice edge position (C(12,4) = 495 states)

**Phase 2** finishes the solve using only the restricted move set {U, D, F2, B2, R2, L2}, which preserves the phase-1 invariant. Coordinates:

- corner permutation (8! = 40320 states)
- UD edge permutation (8! = 40320 states)
- slice edge permutation (4! = 24 states)

Both phases are driven by IDA*: iterative deepening on a heuristic lower bound read from pruning tables. The pruning tables store the exact minimum distance to the goal for coordinate pairs (twist×slice, flip×slice for phase 1; corner-perm×slice-perm, edge-perm×slice-perm for phase 2), generated by backward BFS from the solved state. Move tables map each (coordinate, move) pair to its successor coordinate, so a search node is a handful of integer table lookups.

All move and pruning tables are built once at startup and serialized to `kociemba_cache.bin` in the working directory; subsequent runs load the cache instead of rebuilding. If the search exceeds its configured depth limits (phase 1 ≤ 12, phase 2 ≤ 18), the solver falls back to replaying the inverse of the recorded move history — this only works for states reached through in-app moves, not painted states.

## Build

Requirements: Windows, Visual Studio 2022 (v143 toolset), and raylib.

1. Install raylib so its headers and `raylib.lib` are on the MSVC include/library paths (e.g. via [vcpkg](https://vcpkg.io): `vcpkg install raylib:x64-windows`, or set the paths under *Project → Properties → VC++ Directories*).
2. Open `rubixcube.slnx` (or `rubixcube.vcxproj`) in Visual Studio.
3. Build `Release|x64` and run. `Roboto-Medium.ttf` must sit next to the executable for the custom font; the app falls back to raylib's default font if it's missing.

Note: the project file does not pin raylib paths, so a fresh machine needs the include/lib directories configured as above. Build not verified on a clean checkout — no MSVC toolchain was available at packaging time.

## Controls

| Input | Action |
|---|---|
| Left-drag | Orbit camera (right-drag in paint mode) |
| Scroll wheel | Zoom |
| `U` `D` `F` `B` `R` `L` | Face turn (hold `Shift` for counter-clockwise) |
| `Space` | Scramble (25 random moves) |
| `X` | Solve |
| `Enter` | Reset to solved |
| `P` | Toggle paint mode |
| Left-click sticker | Cycle sticker color (`Shift`-click cycles backward); centers are locked |
| `V` | Validate painted state |
| `M` | Toggle step mode |
| `N` | Advance one solution move (step mode) |
| `C` / `S` | Toggle cubies / stickers |
| `T` | Toggle solver debug overlay |
| `H` | Toggle UI |

## Known limitations

- Phase-1 depth is capped at 12 and phase-2 at 18; unusually deep states can exceed the limits and trigger the inverse-history fallback (or fail outright for painted states).
- The pruning tables are coordinate-pair tables, not the larger three-coordinate tables from the reference implementation, so node counts are higher than optimal.
- Windows/MSVC only; no CMake or cross-platform build files.
- The solver is single-threaded and runs on the UI thread — the window blocks while a deep search runs.
